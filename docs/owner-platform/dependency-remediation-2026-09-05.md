# Owner-only dependency remediation — 2026-09-05

## Scope and rationale

This change affects only `owner-platform/package.json` and its lockfile. It does
not upgrade the public application, add a CMS bridge, change visual components,
or authorize deployment. The protected public checkpoint remains
`0f0adf686b2752e23c25d224f8c60815b10fd451`.

The owner audit identified DOMPurify 3.4.8 through Monaco 0.56.0. Monaco pins that
version exactly, so a normal install could not select its patched replacement.
A scoped `monaco-editor` override now selects DOMPurify **3.4.14**, leaving other
dependency consumers unrestricted. The upstream [3.4.14 release](https://github.com/cure53/DOMPurify/releases/tag/3.4.14)
and [affected-version advisory](https://github.com/advisories/GHSA-55q2-fjhq-7xh7)
were reviewed before the change. This override should be reconsidered when Monaco
ships a compatible dependency update, not left indefinitely without review.

`npm ls esbuild dompurify --depth=5` also reported an invalid dependency tree:
Vite 8.2.2's esbuild peer range did not accept the hoisted 0.25.12. The owner now
pins **esbuild 0.28.2** as a development dependency. Vite, tsx and esbuild-register
resolve that version; drizzle-kit retains its own compatible 0.25.12. The older
0.18.20 inside `@esbuild-kit/core-utils` is deliberately not force-overridden
across major API ranges.

The lockfile was regenerated by npm. Its relatively large diff includes platform
binary relocation and dependency metadata changes. A semantic comparison of
resolved URLs/integrities found no changed non-esbuild package other than
DOMPurify. No root manifest or root lockfile was modified.

## Security result and limitations

After `npm ci --ignore-scripts`, `npm ls esbuild dompurify --depth=5` exits 0 with
no invalid peer dependency. `npm audit --omit=dev` reports **12 moderate affected
packages; 0 low, high or critical**, down from 14 affected packages (1 low and
13 moderate). Those package counts include propagation through dependent
packages; they are not twelve independent vulnerabilities.

Two underlying advisory chains remain:

- [Payload unlock access](https://github.com/advisories/GHSA-jg8r-5jh2-v2xj): the
  installed 3.88.0 remains in the affected range. This project's Users collection
  already requires `ownerOnly` for `unlock`; that explicit access rule does not
  turn an affected dependency into a clean audit.
- [esbuild development-server exposure](https://github.com/advisories/GHSA-67mh-4wv8-2f99):
  the old esbuild-kit loader chain remains. Development and QA services must stay
  loopback-only. Do not expose them as production services.

The public application's separate moderate `fflate` finding is untouched.
Deployment remains blocked under the operations policy. Do not run npm's proposed
Payload adapter downgrades or `npm audit fix --force`. Re-audit before any release;
registry results are time-dependent.

## Verification procedure

Run the owner clean install, dependency tree check and full `npm run check`.
Then exercise the real isolated Payload editor using
`tests/media-editor.browser.mjs`, with synthetic QA credentials and database.
This checks admin loading and draft persistence after the dependency change;
it is not an upstream DOMPurify exploit reproduction or a production security
certification. Do not use the real owner's database for this test.

Run root unit tests, lint, typecheck, public guards and isolation tests. Build a
fresh `build:public-proof` artifact and run `check:owner-isolation` against it.
Keep the fixed checkpoint comparison tolerance unchanged. Results are recorded
below only after those commands complete.
